Chatbot architecture improvement plan: problems, solutions, and implementation phases

6 core problems with the current system

Critical Responses.json has wrong/missing data
Problem
Contact info says "Please visit our website" but bulliesandco_final_data.json has real emails and phone. Privacy question triggers RETURN_POLICY (wrong intent). LLM hallucinated generic responses instead of using actual crawled data.
Fix
Rebuild the LLM prompt to explicitly inject actual contact fields. Separate PRIVACY intent from RETURN_POLICY. Add a post-processing validation step that checks responses against real data fields before saving.
Critical Intent detection is too rigid
Problem
"give me support emails" → matched PRODUCT_SEARCH because "give" and "emails" triggered different word lists. Keyword matching fails whenever users phrase things differently than the hardcoded words. "What's the cheapest?" misses BUDGET_FILTER because it has no number.
Fix
Replace keyword matching with BM25 search over a pre-indexed document corpus. BM25 ranks all documents by relevance score — no hardcoded phrases needed. Users can say anything and the most relevant knowledge document wins.
High No context between turns
Problem
"i want product under 100" → generic response. "what?" (follow-up confusion) → bot ignores prior context entirely and gives an unrelated answer. Each message is treated as a fresh, isolated query.
Fix
Add a session memory object that tracks last entity, last intent, entity history, and user preferences. Before BM25 search, run pronoun/ellipsis detection. If "it/this/that" or a very short query is detected, resolve it from memory before searching.
High Duplicate products in responses.json
Problem
Gold Cuban Choke Chain has two slugs: collections_frontpage_products_cuban-choke-chain-gold AND products_cuban-choke-chain-gold. Product matching wastes cycles and can return duplicate/conflicting responses for the same product.
Fix
Deduplicate by product name (not slug) during BM25 index construction. If two slugs have the same product name, merge them into one indexed document. Add a dedup step in the LLM processor before saving.
Medium Progressive variation counter is per-intent, not per-product
Problem
intentCounters tracks how many times PRICE was asked globally, not which product. Asking price of Gold chain, then price of Silver chain, gives variation 1 then variation 2 — but both should start from variation 1 (short answer) for their own product.
Fix
Track counters as intent:product_slug keys, e.g. PRICE:gold-cuban-choke. Each unique combination of intent + entity gets its own progression independently.
Low No out-of-domain guard
Problem
If user asks "what's the weather?" or "write me a poem," the bot attempts to find a match and falls through to a generic response that looks like a bug, not a graceful deflection.
Fix
Use BM25 score threshold. If the top document scores below ~0.4, trigger an out-of-domain response: "I'm here to help with Bullies & Co products, policies, and ordering. What can I help you with?"

New system flow — query runtime

Step 1 — Context check (before anything else)
User message arrives
→
Pronoun/ellipsis detection
→
Memory lookup
Check if message contains "it", "this", "that", "and", or is under 4 words. If yes, attempt to resolve the missing entity from session memory before proceeding. If memory is empty, proceed normally.
Step 2 — BM25 search over indexed corpus
Cleaned query
→
BM25 rank all documents
→
Top N results + scores
The BM25 corpus is built once from final_data.json — products (3-4 docs each), policies, about, contact, FAQ questions. ~60 documents total. Returns relevance scores for every document.
Step 3 — Intent + entity resolution from top results
Score ≥ threshold?
→ No →
Out-of-domain deflection
Score ≥ threshold?
→ Yes →
Read metadata from top doc
→
Intent + entity known
Each BM25 document carries metadata: {type, intent, product_slug}. Top result's metadata tells the system exactly which response pool to use.
Step 4 — Response pool selection
Product-specific path
intent=PRICE + product matched → product_responses[slug].price_responses
Generic intent path
intent=SHIPPING, no product → responses.SHIPPING
FAQ path
BM25 matched a FAQ document → faq_responses[i].responses
Out-of-domain path
All scores below threshold → deflection message, ask to rephrase
Step 5 — Variation selection and naturalization
Use intent:product_slug counter key to pick the progressive variation. Optionally prepend a short acknowledgment fragment ("Sure!", "Got it —") and append a relevant call-to-action ("Want to see other sizes?" / "Need anything else?") to make responses feel less robotic.
Step 6 — Memory update
After every successful response: write the resolved entity, intent, and product slug to session memory. Push to entity history stack (keep last 5). Store any preference hints (budget mention, color preference). This feeds the context check in step 1 for the next turn.

Pros and cons of BM25 for this use case
Pros
Zero server cost — runs entirely in the browser as JS
Handles synonyms and rephrasing naturally via IDF scoring
Returns confidence scores — enables out-of-domain guard
No API dependency — works offline
~1ms query time for 60 documents
No training needed — index is built from static JSON
Cons
Doesn't understand semantics — "inexpensive" won't match "cheap" unless both are indexed
Order of words doesn't matter — "not expensive" and "expensive" score similarly
Typos cause misses — "shiping" won't match "shipping"
Requires careful document construction — bad text = bad results
No multi-language support by default
Mitigations for the cons
For synonyms: expand every intent doc with common synonyms in the indexed text. For typos: add Soundex-lite normalization (replace simple misspellings before BM25 search). For "not expensive": keep the existing intent detection as a pre-pass layer — if BUDGET_FILTER keywords are found, skip BM25 and go direct.

Bot

→ Memory: last_entity="Gold Cuban Choke Chain", last_slug="products_cuban-choke-chain-gold", last_intent="PRODUCT_SEARCH"
User
how much is it?
→ Pronoun "it" detected. Memory has last_entity. Resolve: entity = "Gold Cuban Choke Chain", intent = PRICE (from "how much")
Bot

User
and shipping?
→ Very short. "And" = continuation signal. No new entity mentioned. Same entity assumed. New intent = SHIPPING.
Bot

→ "the silver one" — partial entity + history context. Last entity was a choke chain → likely Silver Miami Cuban Choke Chain. BM25 confirms.

Pros and cons of session memory approach
Pros
Zero cost, runs in browser — no backend needed
Makes chatbot feel dramatically more intelligent
Handles the most common follow-up patterns naturally
Easy to debug — memory is a plain JS object
Cons
No persistence — memory wipes on page refresh
Complex comparisons ("which is cheaper?") need extra logic
Wrong resolution is worse than no resolution — silent errors
Hard to test all pronoun edge cases up front
Key safeguard
Always inject the resolved entity name into the response ("The Gold Cuban Choke Chain is..."). This gives the user an immediate signal that the bot understood correctly — and if it got the wrong entity, the user can correct it in the next turn.

Implementation roadmap — 4 phases

1
Fix what's broken now — data quality
~2 hours · No new architecture needed
  • Edit llm-processor.js system prompt to explicitly include actual contact fields (email, phone, address) from crawled data in the CONTACT slot — not generic "visit our website"
  • Add PRIVACY as a separate intent entry in intent-detection.js (words: privacy, data, personal, information, collected, cookies) and remove it from RETURN_POLICY confusion
  • Add a deduplication step in data-processor.js that merges slugs with identical product names before passing to LLM
  • Fix intentCounters key in chatbot-widget.js to use intent:slug format instead of intent-only
  • Re-run llm-processor.js to regenerate a clean responses.json with the improved prompt
  • Manually verify: CONTACT returns real email/phone, PRIVACY gives correct policy, product prices match final_data.json
2
Add BM25 search engine
~1 day · New file: bm25-engine.js
  • Install or vendor wink-bm25-text-search (tiny, no dependencies, browser-compatible) or implement BM25 from scratch in ~80 lines of JS — the math is straightforward
  • Write build-corpus.js (Node.js script) that reads bulliesandco_final_data.json and generates the 60-document corpus JSON with text + metadata per document
  • Write bm25-engine.js — loads the corpus at startup, builds the inverted index (term → {df, positions}), exposes a search(query, n) method that returns top N docs with scores
  • Add BM25 engine to chatbot-widget.js boot sequence — load corpus JSON alongside responses.json, initialize engine after boot
  • Replace responsesDetector.detect(text) call in doSend() with a BM25 search → metadata read → intent resolution pipeline
  • Add score threshold check (threshold ≈ 0.4) — scores below threshold trigger out-of-domain response
  • Test with the problem queries from the issue log: "give me support emails", "what's your privacy policy", "i want product under 100"
3
Add session memory + context resolution
~half day · Additions to chatbot-widget.js
  • Add sessionMemory object at the top of the widget IIFE with fields: last_entity, last_slug, last_intent, entity_history, budget_hint, turn_count, last_response
  • Write detectContextSignal(text) function — checks for pronouns, short queries, continuation words, color references
  • Write resolveFromMemory(signal, text) function — returns a resolved query string with entity injected (e.g. "it" → "Gold Cuban Choke Chain price")
  • In doSend(), call detectContextSignal first. If a signal is found and memory has data, resolve before BM25 search
  • Write updateMemory(intent, entity, slug, response) — call after every successful response delivery
  • For budget_hint: parse numbers from user messages, store if under 500 (reasonable budget range). Use when BUDGET_FILTER or PRICE intent fires.
  • Test the conversation chain: product → "how much?" → "and shipping?" → "what about the silver one?" — verify entity is injected into each response correctly
4
Naturalization layer (optional polish)
~few hours · Quality-of-life improvement
  • Add acknowledgment fragments array: ["Sure!", "Great question —", "Happy to help —", "Absolutely —", "Got it —"]. Prepend randomly (not every message, ~40% of the time)
  • Add contextual call-to-action fragments by intent: PRICE → "Want to check other sizes?", STOCK → "Ready to order?", SHIPPING → "Need help with sizing first?". Append to ~50% of responses
  • Add anti-repetition guard: compare new response to last_response in memory. If identical, pick the next variation index instead
  • For PRICE responses: append free shipping reminder ("Shipping is free within the US!") on first price query in session
  • Introduce 400–800ms randomized delay variation (instead of fixed 2000ms) to feel more natural
