Bolnee chatbot: complete implementation plan for a fully capable question-answering system

What's actually broken — and why

The root cause isn't the intent detection — it's the responses themselves
Your current responses.json was generated by a small LLM (nvidia/nemotron-3-nano-30b) with a prompt that didn't force it to use real data. Every single response slot got generic filler. The intent detection is the wrong thing to fix first — even perfect routing leads to bad output when the response pool itself is garbage.
Data problemLLM ignored your actual crawled data
What the data has
CONTACT: support@bulliesandco.com, sales@bulliesandco.com, (123) 456-7890, 123 Main St, Anytown USA
Products: real descriptions, 5 size variants per product with individual prices ($38.99–$42.99)
Refund policy: full paragraph text with exact no-return wording
What responses.json actually says
CONTACT: "Please visit our website for contact details" — real data completely ignored
PRICE: "Regular price $38.99, now on sale" — variant pricing ($38.99–$42.99) missing
REFUND: "All sales are final" — the detail about why (sizing issues, no measurement) is missing
Routing problemKeyword matching can't handle real conversation
Failures from actual conversation log
"what products" → "Search for dog collars by size, material, and style" (PRODUCT_SEARCH variation 1, too short)
"what's your privacy policy" → triggered RETURN_POLICY (privacy contains the word "policy")
"give me support emails" → matched PRODUCT_SEARCH ("give" = trigger word)
"contact number?" → returned PRODUCT_SEARCH response — "emails" somehow mapped wrong
"what?" → GENERAL fallback with no context from previous turn
Every single one of these fails at intent level, before even reaching the response
Why BM25 fixes this
BM25 searches across all 60+ indexed knowledge documents statistically. "support emails" lands on the contact document because the word "email" has high IDF weight. "privacy policy" lands on the privacy document because those exact words appear there. No hardcoded phrases needed.
Context problemEvery message is treated as a cold start
Conversation breakdown pattern
"i want product under 100" → generic budget response, no product names
"what?" → GENERAL fallback. Bot has zero memory that the previous exchange was about budget
"what is your policy" → RETURN_POLICY. Bot doesn't know user was confused, not asking about returns
Each turn is completely isolated — no entity tracking, no follow-up detection
Session memory fixes this
A lightweight JS object tracks last_entity, last_intent, entity_history per conversation. "what?" after a budget response → bot reads memory, responds "Sorry, let me clarify — our cheapest option is the Silver Miami Cuban Choke Chain at $36.99." Pronouns and short follow-ups get resolved from memory before BM25 even runs.
Response problemOnly 3 response types per product — massive coverage gap
What the current product entries have
Each product has: about_responses, price_responses, stock_responses. That's it.
Missing entirely: sizing help, material questions, comparison questions, "which should I buy?", variant-specific prices, care instructions, "does it come in X?", "is it good for large dogs?"
New product response pools
Expand to 7 pools per product: about, price, stock, sizing (with actual size variant prices), material, care, and a comparison pool. The LLM upgrade generates all of these from the actual variant data in final_data.json — including "12-inch is $38.99, 20-inch is $42.99" in the sizing pool.
Coverage problemOnly 12 FAQs — real users ask 50+ types of questions
Current FAQ coverage
12 FAQ items, all basic: materials, return policy, shipping, sizing. Missing: "can I attach a leash?", "is this safe for choke training?", "what's the difference between choke and clasp?", "do you have gift wrapping?", "what's the quality like?", "is it scratch-resistant?", "can my dog swim with it?"
Expanded FAQ generation
New LLM prompt generates 40+ FAQs, explicitly covering: product comparison questions, care and safety questions, ordering process, social media, brand story questions, size chart help, and edge cases. BM25 over FAQ corpus means any question close to these gets answered naturally.

Complete system redesign — 5 layers

Layer 1 — Data pipeline (build-time, runs once per website)
1
Crawler → raw_data.json
No change to crawler.py. It already does a good job. Output: products with content blocks, pages with policy text, contact scraping.
2
data-processor.js → final_data.json
Minor improvements: deduplicate products by name (7 unique, not 14), normalize variant prices into array, extract full policy text (currently shipping/privacy say "content" placeholder — fix crawler to grab this), enrich contact with all email/phone fields explicitly.
3
llm-processor.js → responses.json Major rewrite
New prompt uses claude-sonnet-4 or llama-3.3-70b with explicit data injection. Generates 7 response pools per product (not 3), 40+ FAQs (not 12), all intents with rich real data. Output is larger and richer.
4
corpus-builder.js → corpus.json New file
New build step. Reads final_data.json + responses.json and generates the BM25 search corpus: ~80 documents, each with searchable text + metadata (intent, product_slug, pool_type). Runs once after LLM step, output is served alongside responses.json.
Layer 2 — BM25 search engine (client-side JS)
New file: bm25-engine.js. Loads corpus.json at boot. Builds inverted index in ~5ms. Exposes search(query, n) → returns top N docs with relevance scores. Runs entirely in browser — zero server cost, ~1ms per query.
A
Index construction
Term frequency per document, document frequency across corpus, BM25 parameters (k1=1.5, b=0.75). Stopword removal, simple stemming (strip -ing/-ed/-s). Built once from corpus.json on boot.
B
Query scoring
Clean input → tokenize → BM25 score against all documents → return sorted results. Each result carries its document's metadata: intent, product_slug, pool_type (about/price/stock/sizing etc.).
C
Score threshold guard
If top score < 0.35 → out-of-domain. Bot says: "I'm here to help with Bullies & Co products, policies, and ordering — what would you like to know?" No more silent wrong-intent fallthrough.
Layer 3 — Context memory (session-scoped JS object)
Lives in chatbot-widget.js. Written after every bot response, read before every BM25 search. Fields: last_entity, last_slug, last_intent, last_pool, entity_history[5], budget_hint, color_pref, size_pref, turn_count, last_response_text.
A
Pronoun detection pre-pass
Check incoming message for: "it", "this", "that", "one", "those", "them" — or message is under 5 tokens — or starts with "and", "also", "what about", "how about". If triggered, inject last_entity into query before BM25.
B
Entity name injection
Resolved entity is always inserted into the response text: "The Gold Cuban Choke Chain is $38.99" not just "$38.99". User can immediately confirm the bot understood correctly. Wrong resolution is self-correcting in next turn.
C
Preference accumulation
budget_hint: extracted from any number mentioned near budget words. color_pref: detected from color words (gold/silver/rose gold). size_pref: detected from size mentions (12", 14" etc). Used to personalize PRODUCT_SEARCH and BUDGET_FILTER responses.
Layer 4 — Response assembly (enhanced variation picker)
A
Per-entity counter tracking
Counter key: intent:product_slug e.g. PRICE:gold-cuban-choke. Asking price of gold chain then silver chain gives variation 1 for each — not variation 1 then 2 globally as it does now.
B
Natural language fragments
Optional pre-fragments (~40% of responses): "Sure!" / "Happy to help —" / "Great question —". Optional post-fragments by intent: PRICE → "Want to see sizing options?" / STOCK → "Ready to order?" / SHIPPING → "Need sizing help first?" Makes responses feel less robotic without changing the core answer.
C
Anti-repetition guard
Compare assembled response to last_response_text. If identical string, bump variation index by 1. Prevents bot from saying the exact same sentence twice in a row.
Layer 5 — LLM fallback (optional, for truly unknown questions)
When BM25 score is between 0.35 and 0.55 (low confidence but not fully out-of-domain), optionally route to a minimal Anthropic/Nvidia API call with the website's full context injected as system prompt. This handles the long tail of questions that don't match any pre-generated response. Budget: ~3–5 API calls per conversation max. On/off toggle via BotConfig.

Pros and cons
Pros
Zero cost — runs entirely in browser
No API calls — works offline
~1ms query time for 80 documents
Handles rephrasing without hardcoded rules
Confidence scores → out-of-domain detection
Portable to any customer's site — runs from corpus.json
Cons + mitigations
"Inexpensive" ≠ "cheap" unless both in corpus → mitigated by synonym expansion in intent docs
Typos cause misses → mitigated by simple Levenshtein correction for common words
Word order ignored → mitigated by phrase-matching boost for key multi-word terms
Needs good corpus text → fully under your control via corpus-builder.js
