Here's the full picture based on everything I read across your files and both attached conversations.

The core issue is actually two separate problems stacked on top of each other:

The first is a data quality failure — your llm-processor.js prompt never told the LLM to actually use the real contact fields (support@bulliesandco.com, phone number) from the crawled data. The LLM defaulted to generic placeholders because the prompt didn't make it explicit enough. This is fixable in an afternoon by tightening the prompt and re-running it.

The second is a structural limitation — keyword matching simply cannot handle the variety of real user language. "Give me support emails" has no overlap with any CONTACT trigger word in the current intent list. BM25 solves this because it scores all ~60 documents by relevance, so "emails" naturally surfaces the contact document even without hardcoded phrases.

What I'd recommend doing in order:

Start with Phase 1 today — fix the data and re-run the LLM processor. This alone will eliminate several of the bad responses you showed (wrong contact, wrong privacy policy). Then build the BM25 engine in Phase 2, which is the bulk of the work. The memory system in Phase 3 is what makes it feel genuinely conversational rather than just more accurate.

The biggest risk with BM25 is document quality — if the indexed text for a product is thin or poorly worded, matches will be weak. The build-corpus.js script in Phase 2 is worth spending time on to make the document text rich and varied.
